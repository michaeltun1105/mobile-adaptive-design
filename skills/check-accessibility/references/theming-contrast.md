# Accessibility, colour theming and contrast

Read when building the design system, theming, or running the contrast audit. Scripts: `scripts/theme-generate.mjs`, `scripts/apply-theme.js`, `scripts/contrast-audit.js`.

### Accessibility
- Body text ≥ **12sp**; text contrast ≥ **4.5:1**; non-text (icons, surfaces) ≥ **3:1**; more than one cue for links. [A11Y]
- Touch targets ≥ **48dp** (may extend past the visual). Don't rely on gestures alone (e.g. swipe-to-delete also needs a button). Label icons/images; decorative images get no description. [A11Y]
- **WCAG ratios** [CCA]: normal text AA **4.5:1** (AAA 7:1); large text (≥ 24px, or ≥ 18.66px bold) AA **3:1** (AAA 4.5:1); icons / UI components / graphics **3:1**. Exempt: disabled (inactive) UI, logos and brand marks, decorative images. Low opacity and thin weights lower real contrast.
- **Pair colours by tone (luminance), not hue** [CCA, MCU]: HCT tone 0 = black … 100 = white. A tone difference of **≈ 40 guarantees 3:1, ≈ 50 guarantees 4.5:1**. White text on a filled colour therefore needs that colour at **tone ≤ 50**. Start in grayscale to set hierarchy, then map colour roles.


### Color theming (M3 scheme from the brand colour) [MTB, MCU, CCA]
- An M3 scheme is generated **from one source colour** (the brand). The algorithm keeps the brand's **hue and chroma** but sets each role's **tone** for contrast — so the brand hex usually does **not** appear in the scheme (example: source #0096D6 → Primary #256489 = tone 40, Primary Container #C9E6FF = tone 90, Dark Primary #95CDF7 = tone 80 — always compute the real values for the product's own brand). This is expected; explain it when the person can't find the brand hex.
- **Variant:** `SchemeTonalSpot` = MTB default (light tinted containers; recommended). `SchemeFidelity` ≈ MTB "Color Match" (closer to the brand, but Primary Container becomes a saturated dark colour with white text — rail indicator and chips turn dark).
- **Modes:** generate **Light and Dark** by default (contrast level 0). Medium/High contrast (0.5 / 1) only when the person asks — teams found 2 modes enough.
- **No plugin needed (default method):** run MCU in the workspace (`npm i @material/material-color-utilities@0.3.0`; Node script: `new SchemeTonalSpot(Hct.fromInt(argbFromHex(brand)), isDark, 0)`, then `MaterialDynamicColors[role].getArgb(scheme)` for the 49 roles `Primary … Surface Container Highest`). Create a local variable collection `M3 Theme · <Product> (<#brand> · Tonal Spot)` with modes Light / Dark and variables named like the kit: `Schemes/<Role>` (scopes fills/strokes/effects). Add `Source/Brand = <#brand>` (all modes, scopes [] — reference only) and put source, variant, library version in the collection description. The plugin route (MTB plugin → Create theme → Swap) is an alternative when the team wants to tweak colours in a UI.
- **If the file already has a collection `material-theme`** (an old MTB export) check its Primary: `#65558F` means it is still Google's baseline purple — update that collection to the brand instead of creating a second one, after asking.
- **Brand override:** if the person wants the exact brand hex on buttons, set `Schemes/Primary` (+ `Surface Tint`) of the Light mode to the brand and note it in the variable description. Overriding a generated colour **removes the contrast guarantee** [CCA] — check the tone: a brand above tone 50 fails 4.5:1 for white labels (example: #0096D6 is tone 58.7 → 3.32:1). Offer the closest passing colour: same hue/chroma, highest tone with `Contrast.ratioOfTones(100, tone) ≥ 4.5` (example: #0096D6 → #007DB4, tone 49.5, 4.57:1 — compute it for the actual brand). Then add `Custom/Primary Text` = generated tone-40 Primary (Light) / tone-80 (Dark) for brand-coloured **text and icons on surfaces and tinted containers**; content inside Primary Container uses `On Primary Container`.
- **Applying the theme (kit library variables can't be edited from a consuming file, so rebind per node with a script):** walk the target section (`skipInvisibleInstanceChildren = false`), for every SOLID fill/stroke: bound to a remote `Schemes/<Role>` → local `Schemes/<Role>`; using an M3 style `M3/sys/light/<kebab-role>` → bind the local variable of the Title-Case role and clear the style (`setFillStyleIdAsync('')`). Overrides inside instances are allowed. Set the collection mode on each screen frame (`setExplicitVariableModeForCollection`). Re-run after adding kit components.
- **Mapping a team's semantic colours to M3 roles** (only when the person wants the whole screen themed, e.g. to get Dark mode): text/primary → On Surface · text/secondary → On Surface Variant · text/disabled → On Surface @ 38% · text/muted → Outline · text/accent, status/info, action/primary-bg → Primary · text/inverse, white text/icons on primary → On Primary · background/default → Surface · background/surface → Surface Container · background/interaction → Secondary Container (strokes → Outline Variant) · background/accent-surface → Primary Container · border/default → Outline Variant · white shapes → Surface Container Lowest; large hard-coded white screen/card fills → Surface / Surface Container Lowest. Keep success/warning/error-type status colours and third-party logo colours as they are (no M3 role / brand marks). Build the result as copies (`M3 Light · …`, `M3 Dark · …`) next to the original so the team can compare.
- **Handoff:** the same values export to Jetpack Compose (`Color.kt` / `Theme.kt`: `lightColorScheme(...)`, `darkColorScheme(...)`) — offer to generate them from the MCU output.
